## 1. 文档目标与证据规则

### 1.1 文档目标

本文要解决五个问题：

1. 云枢从产品目标到当前实现经历了什么开发阶段。
2. 各项关键技术为什么被选择，模块之间怎样协作。

4. 这些问题如何被转化为代码约束、状态机、数据协议、测试或发布门禁。
5. 哪些方法可以直接复用于其他本地优先 AI 桌面应用。

### 1.2 证据等级

本文用以下标记控制结论强度：

| 标记 | 含义 | 可以作为发布事实吗 |
| --- | --- | --- |

## 2. 执行摘要

云枢是一个中文、本地优先、以 Obsidian 为知识数据库的 macOS 与 Windows 桌面 Agent。它的核心难点不是“调用模型”，而是让模型参与复杂知识工作时仍保持权限可控、原文不失真、状态可恢复、结果可审计。

当前实现形成了以下主线：

1. 使用 Vanilla JavaScript + Vite 提供单窗口桌面体验，使用 Tauri 2 + Rust 承担原生能力、安全边界和本地持久化。
2. 明确双权威边界：Obsidian Vault 管知识内容；SQLite 管任务、会话、计划、配置、回执和操作状态。
3. 把模型输出降级为候选数据。模型不能直接调用文件、网络、Shell 或设置。
4. AI 助手驱动的业务操作以 `Command Bus → Policy Engine → Task Runtime → 能力/适配器 → Operation Event` 为主链；当前仍有若干专用 Tauri 命令不由通用中间件机械覆盖。
5. 用一次性模型意图回执把“模型确实分析过”变成可消费的授权前置证据，阻止前端伪造模型决定。
6. 把大文件处理设计成分块上传、流式暂存、哈希核验、分批模型分析和分层汇总，而不是设置任意总大小上限或静默截断。
7. 把“来源忠实层”和“模型理解层”拆成两个关联交付物：用户 Vault 保存原文与原位附件，Agent 库保存结构化理解稿、逐图观察、标签和 Wiki Links。
8. 把图片内容身份 `asset_id` 与出现位置 `reference_id` 分开，解决“同一图片只分析一次”与“每个位置都要保真”之间的冲突。
9. 用完整性门禁把 Office 位置关系、外链图片、本地附件映射和双 Vault 提交从“尽力而为”提升为阻断条件。
10. 用 SQLite 事务、WAL、`synchronous=FULL`、迁移、完整性检查、在线备份和恢复安全点承载长期运行。
11. 用发布审计、Schema 校验、第一方 Skill 来源校验、代码模式质量门禁、Rust 格式/Clippy/测试和双平台打包配置形成多层验证设计。
12. 当前主要技术债是超大单文件、真实端到端测试不足、外部连接器 SSRF 防线弱于采集链、签名/公证与正式 Release 自动化未完成。

## 3. 产品起点：先定义不做什么

### 3.1 产品目标

**已验证事实**：`docs/PRODUCT_REQUIREMENTS.md` 将产品定义为：用户通过 AI 助手完成知识采集、整理、查询、创作、复盘、报告、Skill 调用和知识库维护，同时始终拥有自己的 Markdown、附件和 Vault。

这一定义带来三个直接工程要求：

- 数据不能被锁进云端私有格式，最终知识必须落到用户可读、可迁移的文件中。
- AI 助手不能只返回文字，要能驱动持续任务并给出真实运行结果。
- “智能”不能以牺牲本地边界、来源忠实度和用户确认权为代价。

### 3.2 产品原则如何转成工程约束

| 产品原则 | 工程化表达 |
| --- | --- |
| 本地优先 | Tauri/Rust 本地运行；SQLite 与 Vault 保存在设备；无账户系统和默认遥测 |
| 用户拥有知识 | Markdown、Properties、附件、标签和 Wiki Links 写入 Obsidian |
| 普通聊天不产生副作用 | 对话与执行意图分流；普通聊天只保存本地会话 |
| AI 不能自行扩权 | 候选意图、能力白名单、一次性回执、确定性 Policy Engine；当前强制范围见 6.4 |
| 结果必须真实 | 任务状态、步骤、检查点、错误和操作事件来自实际执行 |
| 来源不能被摘要冒充 | 用户 Vault 保存忠实原文；Agent 库保存模型理解稿 |
| 设置只属于用户 | 应用命令层禁止助手写设置；设置由直接用户来源修改 |
| 删除和外部发送高风险 | 策略返回 `require_approval`，并要求检查点或显式确认 |

### 3.3 `0.1.2` 明确不包含的范围

以下都是**明确延期**，不能因为代码里存在相关名词或候选字段就描述成已上线：

- 实体知识图谱、实体消歧、类型化实体关系和多跳查询。
- 神经 Embedding 管线、远程向量数据库和学习式语义重排；本地确定性特征向量与 RRF 已纳入当前实现。
- 账户注册、登录、云端身份隔离。
- 通用远程控制入口和未经用户配置的外部消息投递。
- 绕过登录、Cookie、验证码、DRM、加密流媒体或平台访问控制。
- 自动下载安装更新、Apple 签名和公证。

这一步的可复用经验是：**先建立“非目标清单”，再写功能清单**。对 AI 产品尤其重要，因为模型很容易把规划、提示词能力和真实系统能力混为一谈。

### 4.2 阶段一：一次性建立可运行基线

首个提交不是脚手架，而是一个体量很大的功能基线：

- `desktop-ui/app.js` 当时新增 10,321 行，形成十个主工作区和大量前端工作流。
- `runtime_db.rs` 当时新增 3,021 行，承担本地结构化状态。
- `obsidian.rs` 当时新增 2,287 行，建立 Vault 发现、读取、写入和索引边界。
- `model_provider.rs` 当时新增 1,886 行，提供模型供应商、请求和解析能力。
- `capture_pipeline.rs` 当时新增 978 行，建立采集执行骨架。
- 同时加入产品、架构、品牌、AI 助手契约、JSON Schema 和四个第一方后台 Skill。

**证据支持的推断**：这一阶段采取了“先建立完整纵向切片”的策略。优势是很快把 UI、模型、本地状态、知识写入和内容处理连成系统；代价是多个核心文件在第一阶段就很大，后续演进更依赖回归门禁。

阶段一最重要的决策不是某个库，而是双权威模型：

```text
知识正文、附件、人类可读关系  → Obsidian Vault
任务、会话、计划、配置、回执  → SQLite
搜索索引                         → 可重建派生层
```

如果没有这条边界，后续会出现“数据库与 Markdown 谁说了算”“用户手工改 Vault 后怎样同步”“索引损坏能否重建”等根本冲突。

### 4.3 阶段二：从功能集合升级为受控运行时

该提交新增四个具有治理意义的模块：

- `command_bus.rs`：定义类型化 `ApplicationCommand` 和命令执行入口。
- `policy.rs`：对来源、标识符、路径、网络、预算、能力和副作用类别做确定性判断。
- `task_runtime.rs`：定义任务状态机和合法迁移。
- `obsidian_management.rs`：把笔记、目录、属性、标签、链接、Graph、回收和恢复等管理动作集中到原生边界。

同时增加：

- 发布源码审计脚本。
- Issue 与 Pull Request 模板。
- `CHANGELOG.md`、`CONTRIBUTING.md`、`SECURITY.md`。
- 双语架构图与更完整的公开文档。

**证据支持的推断**：开发中意识到“前端调用很多原生命令”不足以证明系统安全，因此把权限、状态和副作用抽成可检查的共同路径。这个阶段把系统从“有功能”推进到“功能有统一执行语义”。

### 4.4 阶段三：补齐长期运行与交付闭环

该阶段增加和强化：

- `.github/workflows/ci.yml`：配置为在 macOS 上执行发布审计、依赖安装、完整验证和未签名 Debug 应用构建。
- `scripts/quality-gates.mjs`：把关键产品约束编码为源码级回归检查。
- `connectors.rs`：受控外部投递配置与调用边界。
- `updater.rs`：稳定 Release 查询、SQLite/Vault 保护点和本地回滚。
- `runtime_db.rs` 大幅扩展，加入长期记忆治理、模型用量、取消、更新保护和更多运行状态。
- 模型、采集和 Obsidian 链路继续强化，形成较完整的端到端结果回传。

这一阶段解决的是“应用运行一天之后会怎样”：

- 任务失败后是否可重试。
- 请求取消是否有记录。
- 长期记忆是否可纠正、替代和墓碑化。
- 更新前是否有保护点。
- 外部投递是否仍受确认和日志约束。
- 源码是否能在纯净检出中验证。

### 4.5 阶段四：消除大输入与 Office 保真短板

该阶段最显著的变化是新增三套 OOXML v2 解析器，并重写采集输入路径：

- Word：保留正文、表格、页眉页脚、脚注尾注、批注、分节、图片字符位置和上下文。
- Excel：保留全部工作表、坐标、普通/共享公式、缓存值、Drawing 锚点；不伪装公式已重新计算。
- PowerPoint：按 `sldIdLst` 真实顺序保留元素边界、层级、裁剪、表格及幻灯片/版式/母版来源。
- 每个解析器都输出 `integrity.status/errors/checks`，关键结构缺失时阻断双库写入。

同期解决了四类输入问题：

1. 本地文件从一次性 IPC 载荷改为 `begin → append_chunk → finish`。
2. 模型正文按 UTF-8 字节边界分批，批次结果再分层汇总，不再静默截断。
3. 对话图片首次分析后持久化视觉记录，普通历史不重复发送 Data URL。
4. 图片分析把内容级身份和位置级身份分离，既去重又保留原位语义。

### 4.6 当前快照：Windows 产品化补充

当前源码进一步加入：

- Windows.Data.Pdf PDF 渲染辅助程序。
- Windows Imaging Component 图片解码与模型派生图辅助程序。
- Media Foundation 媒体解码、抽帧和 PCM 音频生成。
- SAPI 本地语音识别，并对语言识别器缺失返回明确错误。

**当前风险/缺口**：这些能力可由当前文件和质量门禁证明，但不能写成某个具体 Git 提交的历史成果，直到快照被正式纳入可达历史。

### 4.7 实际开发流程：从产品目标到可发布快照

前面的四阶段时间线描述了“何时出现了哪些成果”；本节补充“这些成果应如何被做出来、每一轮开发怎样闭环”。

**证据支持的推断**：仓库没有逐日站会记录、任务看板或每个功能的 PR 讨论，因此不能逐小时还原实际开发顺序。以下流程以可达提交的模块变化、当前实现的依赖关系、架构约束和验证脚本为依据重建；其中“已落地的步骤”与“应持续复用的标准步骤”会明确区分。

#### 4.7.1 宏观开发流程

```text
产品目标与非目标
→ 架构权威边界
→ 协议与数据模型
→ 最小纵向切片
→ 副作用治理与持久任务
→ 内容/模型/文件完整性强化
→ 跨平台适配与安装验证
→ 自动化质量门禁
→ 发布审计、文档、回滚准备
→ 复盘并把新风险写回不变量
```

这不是瀑布式“一步结束后永不回头”的流程。云枢的提交史表明，采集、模型、数据库、Vault 和 UI 是反复联动改造的：后续阶段发现大文件、图片位置、Office 结构或 Windows 安装问题后，会回到协议、原生实现、前端状态和质量门禁一起修改。

| 流程阶段 | 开发时先回答的问题 | 主要工作 | 形成的可审计产物 | 进入下一阶段的最低条件 |
| --- | --- | --- | --- | --- |
| 1. 产品定界 | 用户真正拥有的是什么？当前明确不做什么？ | 写 PRD、非目标、用户工作区和隐私边界 | `docs/PRODUCT_REQUIREMENTS.md` | 不能把规划能力写成当前能力 |
| 2. 架构定界 | 知识、运行状态、模型建议和授权分别由谁负责？ | 定义 Vault/SQLite 权威、模块职责、威胁模型 | `ARCHITECTURE.md`、AI 助手契约 | 每类数据有唯一权威与恢复策略 |
| 3. 协议定界 | UI、模型、原生层和 Skill 交换哪些结构化数据？ | 定义 Schema、命令字段、回执、任务、计划、记忆和 Skill manifest | `docs/schemas/`、Rust struct、JSON contract | 不能依赖自由文本或未约束对象驱动副作用 |
| 4. 最小纵向切片 | 从一条用户输入到一个真实结果最短的可运行路径是什么？ | 搭建 Vite UI、Tauri、模型网关、SQLite、Vault 读写、基础采集 | `f4d7f53` 中的 UI、数据库、Obsidian、模型和 Skill 基线 | 能产生真实持久化结果，而不是演示状态 |
| 5. 治理补齐 | 谁能执行？什么路径、预算、审批和状态允许执行？ | 加入命令总线、策略、状态机、检查点、事件、授权门 | `8d39a8a` 的运行时治理模块 | 失败、取消、重试和审批有确定语义 |
| 6. 内容完整性 | 大输入、外链、Office、图片和外部编辑怎样不丢数据或越权？ | 分块上传、流式暂存、哈希、位置 ID、双 Vault、完整性门禁 | 采集管线、OOXML v2、附件映射、质量检查 | 未完整内容不能被标成成功 |
| 7. 交互整合 | 用户如何看到真实进度、失败、待确认和恢复选项？ | 十个工作区、任务抽屉、引导、确认、操作日志和无障碍 | `desktop-ui/`、前端质量门禁 | UI 状态可回溯到任务/文件/事件事实 |
| 8. 平台与交付 | 安装包是否携带且能调用所需运行时？ | macOS/Windows 原生辅助程序、嵌入式 Python、打包资源映射 | Windows 构建与安装验证脚本 | 不是只完成编译，还要验证安装后资源 |
| 9. 验证与发布 | 干净源码、协议、运行时和文档是否一致？ | 发布审计、Schema、Skill、质量门禁、fmt、Clippy、测试、打包 | `scripts/`、workflow 配置、协作文档 | 发布证据与未验证边界都写清楚 |
| 10. 复盘回灌 | 本轮最危险的失败模式是什么？ | 将风险升格为不变量、测试、质量门禁、文档和路线图 | 问题台账、P0/P1 计划、回归测试 | 同类问题不能只靠开发者记忆避免 |

#### 4.7.2 开发启动：先写“不能错什么”

云枢的开发不是先画页面再补安全。每一个高风险能力在实现前应先写出以下六项：

1. **用户目标**：例如“把 PDF 读懂并保存到个人库”，而不是“调用 PDF 解析器”。
2. **权威数据**：原 PDF、忠实 Markdown、理解稿、任务状态分别落在哪里。
3. **副作用清单**：读取本地文件、访问网络、写 Vault、删除、外部发送、写设置分别是否发生。
4. **信任边界**：用户文本、文件内容、URL、模型 JSON、前端参数都默认不可信。
5. **失败定义**：缺页、缺图、模型超时、磁盘不足、外部文件变化、取消和重试分别向用户返回什么。
6. **验收证据**：哪些哈希、任务状态、写入结果、操作事件、测试和日志可以证明完成。

这六项直接对应后来出现的架构不变量。比如“Office 必需图片丢失”不是一个 UI 提示问题，而是“不能生成完整成功回执”的完整性问题；“模型说要删除笔记”不是模型能力问题，而是审批和路径范围问题。

#### 4.7.3 单个功能的标准开发闭环

建议把任何新能力按下面顺序开发。云枢中采集、报告、Obsidian 管理、模型路由和连接器都应遵循这个闭环。

| 步骤 | 具体动作 | 交付物 | 常见错误 |
| --- | --- | --- | --- |
| A. 需求拆解 | 写用户触发语句、成功结果、非目标和边界条件 | 场景清单与验收条件 | 直接从“调用哪个 API”开始 |
| B. 风险分级 | 标记读、写、删除、外部投递、设置、网络和长任务 | 副作用矩阵 | 把“保存”和“发送”当成同一种操作 |
| C. 数据设计 | 确定 Vault/SQLite/内存/派生索引的归属，定义 ID 与幂等键 | Rust 类型、Schema、迁移草案 | 一个 JSON 同时充当原文、缓存和授权 |
| D. 原生最小实现 | 先在 Rust/Skill 实现确定性输入校验、资源处理和错误结构 | 单一能力的可调用原生接口 | 先在 UI 写一大段乐观状态 |
| E. 权限与状态接线 | 为 AI 驱动操作接入命令、策略、任务、审批、检查点和 trace | 命令/策略/任务测试 | 只在前端按钮上隐藏高风险操作 |
| F. 持久化与恢复 | 写事务、原子文件替换、冲突检查、取消、重试和恢复语义 | 数据库迁移、检查点、回滚路径 | 只实现成功路径 |
| G. 前端接入 | 展示真实进度、待确认、错误原因、重复跳过和最终路径 | UI 交互、无障碍状态 | 用模型回复或模拟进度表示完成 |
| H. 对抗性验证 | 输入恶意路径、超大文件、错误 MIME、断网、重复请求、外部修改 | 单测、fixture、手工复现 | 只测一个正常样例 |
| I. 回归固化 | 将最容易被重构破坏的约束编码为测试或质量门禁 | `quality-gates.mjs` 或模块测试 | 只在 issue 中记录“以后注意” |
| J. 文档与交付 | 更新架构、PRD、变更记录、贡献/回滚说明和版本字段 | 可审计变更说明 | 代码完成后文档与真实行为漂移 |

开发完成的判断不是“界面能点”，而是 A-J 全部有可检查证据。对于纯只读功能，E/F 可以较轻；对于写入、删除、联网和外部投递，E/F/I 不能省略。

#### 4.7.4 云枢采集功能的实际开发链路示例

采集是最能说明开发流程的能力，因为它同时涉及用户输入、文件系统、网络、模型、双存储和质量反馈。

```text
用户提出采集目标
→ 识别来源类型与是否存在明确执行意图
→ 生成候选命令并通过本地策略
→ 创建/关联持久任务
→ 输入分块或受控网络访问
→ 第一方抽取与来源/哈希记录
→ 模型按字节/图片绑定分批理解
→ 完整性与重复门禁
→ 生成双 Vault 写入计划
→ 用户确认高风险步骤（若有）
→ 提交、补偿回滚、索引与事件
→ 在原对话和任务页报告真实结果
```

更细的开发与运行分支如下：

1. **识别入口**：UI 接受文本、链接、文件或文件夹；普通对话不会因出现 URL 自动开始采集。
2. **判定执行意图**：模型只给候选 intent/能力/参数；本地意图回执、能力目录和策略决定是否创建命令。
3. **输入落地**：本地文件经 `begin_capture_upload → append_capture_upload_chunk → finish_capture_upload` 进入隔离暂存，不能把整文件塞进单次 IPC。
4. **来源访问**：网页和确定图片依赖使用受控网络路径；普通链接仅保留为不可信来源数据。
5. **第一方抽取**：按扩展名与来源调用文档、网页或媒体 Skill，保留结构化来源、提取内容、附件和文件级错误。
6. **内容身份**：计算规范化内容哈希；已提交、写入中或门禁通过的相同内容返回“跳过重复”，不重复写入或误报失败。
7. **视觉与模型批处理**：文本按 UTF-8 字节分批；相同图片按 `asset_id` 去重，位置按 `reference_id` 保留，模型返回结果必须匹配允许的绑定。
8. **质量门禁**：Office 必需部件、页面、图片关系、外链本地化、附件位置或模型输入不完整时进入阻断错误，而不是写入半成品并显示成功。
9. **双库计划**：先生成个人库/用户指定库的忠实原文计划，再生成 Agent 库理解稿计划；两者复用分析结果但承担不同责任。
10. **提交与补偿**：预检目标、外部变更、哈希和审批有效期，建立写前检查点，逐文件原子替换；同步失败时按检查点补偿回滚。
11. **可见结果**：任务状态、操作事件、索引和对话结果只在实际提交后更新；模型不能提前声称“已保存”。
12. **异常回流**：失败原因回到任务步骤和操作日志，开发中再把可重复的失败转换为测试、质量门禁或新的架构约束。

这个例子说明：用户眼中一次“帮我整理文件”的操作，开发上至少经过输入协议、访问策略、抽取契约、模型约束、数据写入、恢复、UI 状态和测试八类工作，而不是一个模型调用。

#### 4.7.5 开发中遇到问题后的处理流程

云枢后续阶段的处理方式可概括为以下闭环：

```text
发现失败模式
→ 判断是产品边界、协议、实现、数据恢复还是交付问题
→ 把失败写成明确不变量
→ 修正原生实现与前端状态
→ 增加最小可复现测试/质量门禁
→ 更新架构和用户可见错误说明
→ 在干净环境重新验证
```

几个已发生过“设计强化”的典型路径：

| 触发的风险 | 初始不足 | 过程中的改造 | 最终固化 |
| --- | --- | --- | --- |
| 大文件和多文件选择 | 一次性载荷容易造成内存/IPC 压力 | 分块上传、暂存、流式哈希、模型分批 | 上传命令、暂存清理、质量门禁 |
| 图片重复与位置丢失 | 单一图片 ID 无法同时去重和保真 | `asset_id`/`reference_id` 双层建模与绑定 | 附件映射、模型绑定、Vault 测试 |
| Office 结构丢失 | 纯文本抽取不足以支撑知识沉淀 | OOXML v2 解析和完整性状态 | 关键结构缺失阻断入库 |
| 模型可诱导副作用 | 提示词不能承担授权 | 命令、策略、回执、任务状态机 | Policy 测试与运行时记录 |
| Windows 安装后能力缺失 | 本机构建不等于安装包可用 | 打包辅助程序、嵌入式 Python、安装后验证 | Windows workflow 和验证脚本 |

注意：这些是从提交与最终代码可见的“风险强化路径”，不是对每一项都发生过线上事故的断言。

#### 4.7.6 每轮开发的退出标准

在准备提交或合并前，应使用以下出口条件，而不是仅依据主流程演示：

| 维度 | 必须能回答的问题 | 证据示例 |
| --- | --- | --- |
| 功能 | 用户目标是否在真实本地数据上完成？ | 任务终态、写入文件、查询结果 |
| 安全 | 不可信输入是否能扩大权限、改路径或触发网络？ | Policy/路径/SSRF 测试 |
| 完整性 | 是否会静默丢文本、图片、Office 关系或来源？ | 完整性状态、fixture、质量门禁 |
| 失败 | 中断、取消、重复、外部修改和磁盘不足会怎样？ | 状态机、幂等、检查点、恢复测试 |
| 可观察性 | 用户和维护者能否知道实际发生了什么？ | 任务步骤、结构化错误、操作事件 |
| 交互 | 进度、审批和错误是否在原上下文中可理解？ | UI 手工验证、无障碍门禁 |
| 交付 | 源码、版本、依赖、资源和安装包是否一致？ | 发布审计、构建、安装验证 |
| 文档 | 架构、PRD、变更记录和非目标是否与代码同步？ | 文档审阅和版本字段检查 |

#### 4.7.7 当前开发流程的优点与应改进处

**已经体现出的优点**：先建立跨层纵向切片，再把缺失的治理、完整性和交付能力逐步补成硬门禁；遇到风险时通常同时调整协议、实现、测试和文档，而不是只修 UI 表面。

**当前应改进处**：

- 首个提交和后续提交体量较大，难以从历史中逐项追踪需求、设计、验证和回滚决策；后续应将一个功能拆成更小、可独立验证的提交或 PR。
- 当前 `desktop/` 快照没有完整进入可达 Git 历史，导致 Windows 流程与安全增强缺乏正式变更链和远端验证证据。
- effectful Tauri handler 的治理并未由统一中间件机械覆盖，批量跨 Vault 写入也不是崩溃原子；开发流程必须把这两项 P0 缺口纳入每次安全审查。
- Token/成本上限、系统密钥保护、正式签名发布和真实 CI run 仍需从“设计/配置”变成可执行、可审计的实际流程。

## 5. 技术选型与取舍

| 选择 | 采用原因 | 获得的优势 | 代价与边界 |
| --- | --- | --- | --- |
| Tauri 2 + Rust | 桌面能力、较小运行体积、强类型原生边界 | 文件、SQLite、网络、进程和平台能力可集中治理 | Rust/Tauri 构建链复杂；双平台辅助程序增加维护面 |
| Vanilla JS + Vite | 快速实现单窗口复杂交互，依赖少 | 页面结构直观，启动和打包简单 | `app.js` 已达 12,998 行，模块隔离和测试难度上升 |
| SQLite + `rusqlite` | 本地事务、查询、迁移、备份成熟 | 任务和审计状态可靠；无需服务端 | Schema 已到版本 21，迁移兼容和恢复测试成本持续增长 |
| Obsidian Markdown | 用户拥有内容，生态成熟，可直接人工编辑 | 可迁移、可检查、可重建索引 | 文件系统冲突、外部修改、附件路径和跨 Vault 提交更复杂 |
| Python 标准库解析器 | XML/HTML/归档处理表达力强，避免捆绑第三方采集器 | 第一方来源可审计，平台依赖少 | Office 解析代码量很大；Windows 需自带 Python 运行时 |
| 系统原生媒体框架 | 避免引入大型第三方媒体/语音栈 | 符合第一方实现约束，利用系统能力 | macOS 与 Windows 必须维护两套适配；语言/编解码器可用性不同 |
| JSON Schema | 固化消息、任务、计划、记忆、Skill 协议 | 协议可独立验证，减少松散对象漂移 | Schema 与 Rust/JS 结构需要同步维护 |
| AES-256-GCM | 本地加密 API 密钥并验证完整性 | 密钥不以明文进入数据库、Vault 或日志 | 设备 key 与数据库同目录，仍需系统密钥保护、迁移和丢失恢复策略 |

## 6. 最终架构：把权威、判断和副作用分开

### 6.1 模块化单体

云枢选择本地模块化单体，而不是多个拥有模糊权限的 Agent 互相调用。主运行环负责：

```text
理解目标
→ 生成类型化候选命令
→ 执行确定性策略
→ 持久化任务
→ 调度能力
→ 提交文件/数据库
→ 记录操作事件
→ 回到原对话
```

这项选择的价值在于：同一个本地进程可以共享事务、状态和审计语义，同时仍用模块边界约束职责。只有真正需要上下文隔离、独立权限、并行计算或独立验收时，才值得拆分执行单元。

### 6.2 五层职责

| 层 | 主要实现 | 负责什么 | 不负责什么 |
| --- | --- | --- | --- |
| 体验层 | `desktop-ui/` | 对话、十个工作区、输入、进度、确认、结果展示 | 不直接写 Vault、数据库或系统工具 |
| 控制层 | `command_bus.rs`、`policy.rs`、`task_runtime.rs`、`scheduler.rs` | 命令、策略、状态机、调度、幂等和审批 | 不相信模型文字就是授权 |
| 能力层 | 模型网关、第一方 Skill、采集管线、报告、连接器 | 执行受限的具体工作 | 不自行扩大路径、域名、预算或权限 |
| 知识层 | `obsidian.rs`、`obsidian_management.rs`、`vault_watcher.rs` | Vault 发现、读写、附件、索引、冲突、恢复 | 不把 SQLite 当知识正文权威 |
| 运行数据层 | `runtime_db.rs` | 会话、任务、计划、回执、事件、配置、备份、迁移 | 不替代用户可读知识文件 |

### 6.3 三类数据必须分开

1. **权威知识**：Markdown、附件、Properties、标签、Wiki Links、报告。
2. **权威运行状态**：任务、步骤、计划、回执、配置、审批、操作事件。
3. **派生数据**：FTS 和可从 Vault 重建的本地特征向量。

可复用判断方法：如果数据丢失后能从 Vault 重建，它是派生层；如果数据描述执行中发生了什么，它属于运行层；如果用户未来仍应直接拥有和阅读它，它属于知识层。

### 6.4 架构主链与当前机械强制范围

“所有副作用走统一运行时”是架构不变量和 AI 助手业务操作的主流程，但当前源码并不是由一个全局 Command Bus 中间件包住每个 effectful Tauri handler。

`src-tauri/src/lib.rs` 在应用授权后还直接注册了以下专用命令族：

- 模型供应商和外部连接器设置。
- 采集上传、暂存、抽取和图片分析准备。
- Obsidian write plan、asset plan、批量 commit、删除/恢复和属性管理。
- 数据库备份/恢复、长期记忆治理、优化和更新保护。

这些命令并非完全裸奔：许多操作使用应用级授权、路径校验、prepare/commit 审批 ID、哈希、检查点、确认 UI 或模块内策略。但**已验证事实**是，当前全局 invoke 拦截器只统一检查应用是否已授权；它不能证明每个已授权后的副作用都先创建了 `ApplicationCommand` 和 `PolicyDecision`。

因此，本文中的统一主链应理解为业务编排合同，而不是对每个 IPC 调用都已机械证明的性质。当前风险是：若 WebView 被攻破，或未来新增 UI 调用遗漏编排步骤，可能直接触发某个专用原生命令的模块内路径。

推荐收敛方式：

1. Command Bus 接受任务后签发短期、能力范围化的原生执行票据。
2. 每个 effectful handler 校验票据的工作区、任务、operation、参数摘要、审批和过期时间。
3. 只读/准备类命令与提交类命令分开注册；提交 handler 不接受仅由前端自造的状态。
4. 质量门禁生成“effectful command → policy/票据校验”覆盖表，而不是只检查前端 invoke 已注册。

## 7. 从一句用户输入到可审计结果

### 7.1 完整链路

```text
用户消息/附件
→ Model Gateway：回复 + 候选意图
→ 本地能力目录：能力 ID 白名单
→ 一次性模型意图回执
→ ApplicationCommand 反序列化
→ Policy Engine 确定性决策
→ Task Runtime 持久化状态
→ Skill / Capture / Report / Obsidian Adapter
→ 文件和数据库提交
→ append-only Operation Event
→ 原对话中的真实完成/失败结果
```

普通聊天不创建任务、不写入 Vault。只有明确操作意图才进入命令路径。

### 7.2 `ApplicationCommand` 为什么必须类型化

当前命令结构至少包含：

- 命令 ID、类型和来源。
- 自然语言意图和已注册能力 ID。
- 操作名与结构化参数。
- 目标 Vault、相对路径、网络目标和声明范围。
- 最大步骤、运行时间、工具调用、Token 与成本预算。
- 幂等键、trace ID 和一次性模型决定回执。

如果直接执行模型生成的自然语言，系统无法可靠回答：目标路径是否越界、网络域名是否允许、操作是否需要审批、重试会不会重复写入。类型化命令把这些问题变成可校验字段。

### 7.3 Policy Engine

`PolicyOutcome` 枚举定义四种结果：

- `allow`
- `deny`
- `require_approval`
- `allow_with_reduced_scope`

**当前实现边界**：`policy::evaluate` 目前只会返回 `allow`、`deny` 和 `require_approval`；`allow_with_reduced_scope` 是数据库协议和枚举中的预留值，尚无实际降权分支或测试，不能描述成已可用策略能力。

当前确定性检查包括：

- 命令整体大小、标识符格式和字段数量。
- 相对路径空值、绝对路径、`.`、`..` 和穿越。
- 网络目标协议与基本格式。
- 助手来源是否携带模型回执。
- 助手是否尝试写设置。
- 写入/删除是否声明 Vault 范围。
- 步骤上限、工具调用上限和运行时间上限。
- `max_cost` 只校验非负且为有限数值；`max_tokens` 当前没有本地上限校验。
- 删除和外部投递是否必须显式审批。
- 写入和破坏性操作是否要求检查点。

**重要边界**：模型可以建议能力和参数，不能产生最终 `allow`。

### 7.4 一次性模型意图回执

一次性回执解决的是 UI 信任问题：即使前端构造出看似合法的命令，也不能伪称“模型已经分析并决定执行”。

正确流程是：

1. 模型网关分析本轮消息。
2. 原生 `ModelIntentState` 在内存中保存回执，生存期 10 分钟，最多同时保留 512 条。
3. 回执绑定本地工作区、intent、允许的 capability ID 集合、operation 和完整 parameters。
4. 前端提交命令时带回回执 ID。
5. Command Bus 先核对命令与回执完全一致，再执行数据库持久化。
6. 只有持久化成功后才移除回执；持久化失败不会误消耗它。
7. 已消费、过期、越工作区或应用重启后丢失的回执都不能再次创建任务。

模型**分析回执**是另一种对象：用于约束采集分析和双 Vault 写入，当前内存生存期为 30 分钟、最多 512 条。不要把分析回执、意图回执、数据库中的命令/策略记录和外部投递回执混成同一种凭证。

可复用经验：**AI 意图不是授权，但可以被封装成授权流程中的一次性证据**。证据必须可验证、可过期、不可重放，并绑定用户输入、能力和工作区语境。

### 7.5 Task Runtime 状态机

```text
created → queued → running → succeeded
                     ↘ awaiting_approval → queued/running
                     ↘ paused → queued
                     ↘ failed → queued
created/queued/running/paused/failed → cancelled
```

运行时保存进度、当前步骤、预算、检查点、错误、重试次数和 trace ID。`succeeded` 与 `cancelled` 是终态，不能重新启动；失败重试必须走合法迁移，不能直接改数据库状态。

这解决了长任务中常见的五个问题：

- 页面关闭后任务状态仍存在。
- 用户可以暂停、恢复和取消。
- 失败原因与最后检查点可追踪。
- 重试不会绕开幂等与策略。
- UI 展示的是运行时事实，而不是模型声称的进度。

## 8. 应用启动、授权和用户体验

### 8.1 应用级授权门

当前原生命令分发层在应用未授权时，只开放读取和更新应用授权的命令，其余原生命令被阻断。授权后才准备 Vault 和工作区。

这不是替代操作系统权限，而是在产品内部建立统一工作授权：

- 本地文件与媒体处理。
- Obsidian Vault 读写。
- 已配置模型连接。
- 用户主动发起的公开链接采集。

macOS 或 Windows 对文件、麦克风、屏幕等保护资源的系统提示仍然有效，应用不绕过它们。

### 8.2 首次引导

质量门禁要求首次安装引导包含五个有序步骤，并通过版本号持久化：

1. AI 助手。
2. Obsidian。
3. 本地内容分析。
4. 定时任务。
5. 本地安全边界。

引导完成后再进入助手名称、Emoji 头像、回复语言和风格设置。该顺序避免用户在不知道产品边界时先面对大量配置。

### 8.3 十个工作区

前端固定为十个路由与十个视图：AI 助手、仪表盘、采集、搜索、创作、技能、任务、报告、操作日志、设置。

关键交互约束包括：

- 页面内容独立滚动，不能因视口高度而裁切。
- 任务抽屉使用固定覆盖层，不改变主页面宽度。
- 模态框使用 `aria-modal`，动态结果使用 `aria-live`。
- 破坏性确认必须有锁定式开关。
- `/` 命令菜单向输入框上方展开，并提供列表框语义和键盘处理。
- 设置由用户手动进入，不由 AI 助手自动跳转和修改。

### 8.4 前端实现的优势与代价

**优势**：单文件状态和流程对早期纵向开发非常直接；Vanilla JS 不引入额外框架抽象；质量门禁可以静态检查关键 DOM、CSS 和调用模式。

**当前风险/缺口**：`desktop-ui/app.js` 已有 12,998 行，`styles.css` 2,020 行。模型批处理、采集、任务、报告、创作、图片记忆、设置和渲染逻辑集中在同一文件，容易产生隐式状态耦合。后续应按领域拆成 ES modules，并为纯函数和状态转换增加自动化测试，而不是继续扩张单文件。

## 9. 模型网关：把供应商差异留在边界内

### 9.1 路由职责

模型配置支持多个供应商和多个用途：

- 普通对话。
- 内容分析。
- 图片理解。
- 图片生成。
- 图片编辑。

网关兼容常见 JSON、文本和 SSE 响应布局，但不会把供应商返回值直接升级为系统动作。图片请求必须路由到用户指定的图片模型，不能与普通对话端点混用。

### 9.2 请求账本与取消

每次模型请求记录：供应商、模型、用途、状态、Token、耗时、成本来源和错误。API 密钥不进入日志。取消使用请求 ID 写入本地取消标记，任务和 UI 由真实取消结果更新。

这里的经验是：模型调用不是一个 `fetch()`，而是一项具有身份、预算、状态、计量、取消和审计要求的运行时操作。

### 9.3 凭据保护

API 密钥使用设备本地密钥通过 AES-256-GCM 加密后写入 SQLite，并使用作用域相关的附加认证数据绑定上下文。密钥不能进入：

- Obsidian 正文。
- 长期记忆。
- 日志导出。
- 源代码仓库。

设备密钥是数据库同目录的 `yunspire.sqlite.key` 明文 32 字节文件：Unix 创建并收紧为 `0600`，Windows 当前源码没有显式 DPAPI 或专用 ACL 加固。AES-GCM 能防止数据库密文被单独复制后直接读取，并能检测篡改，但不能抵御能以同一用户权限同时读取数据库和 key 文件的本机进程。

**当前风险/缺口**：不使用系统钥匙串、Windows DPAPI 或硬件绑定密钥意味着本机同用户攻击面仍存在；跨设备迁移和设备密钥丢失时也需要更明确的恢复/重新配置体验。

### 9.4 上下文不能用“取前 N 条”处理

实现采用两类压缩：

- 对话在接近配置上下文上限前压缩，而不是固定截取消息数量。
- 大型采集正文按 UTF-8 字节边界分批，每批分析后再层级合并。

字节感知而不是字符数感知非常重要：中文、多字节 Unicode 和供应商请求体开销会让“字符长度”低估实际载荷。

## 10. 采集系统：从任意输入到两份可信交付物

### 10.1 统一流程

```text
来源识别
→ 合法访问与第一方抽取
→ 原文、原位附件、来源证据、内容哈希
→ 模型分批分析与逐图理解
→ 确定性质量门禁
→ 用户 Vault 忠实写入计划
→ Agent 库理解稿写入计划
→ 跨 Vault 批量提交与补偿回滚
→ 索引、任务、操作事件和对话同步
```

任何一步无法保证完整性时，结果必须是失败或待处理，不能以一段模型回复替代真实写入。

### 10.2 本地大文件上传协议

前端与 Rust 之间使用：

```text
begin_capture_upload
→ append_capture_upload_chunk × N
→ finish_capture_upload
```

实现要点：

1. 前端使用 `file.slice()` 逐块读取，避免把整个文件编码成一个 IPC 对象。
2. Rust 为每次上传创建隔离暂存区和不可猜测的暂存标识。
3. 每个块有有界大小，累计字节数必须与声明一致。
4. 完成时流式复制并计算 SHA-256，再把暂存令牌交给抽取器。
5. 失败路径显式丢弃暂存附件。
6. 启动时清理遗留上传、附件和 claim 暂存目录。
7. 文件本身不设置产品级总大小上限，但实时磁盘、内存、解码和供应商请求仍有动态资源门禁。

这一区分很关键：**产品不任意拒绝大文件，不等于允许单次无限内存或无限模型请求**。

### 10.3 第一方抽取器

当前后台 Skill 覆盖：

- Markdown 美化。
- 文档内容分析：TXT、Markdown、PDF、Word、Excel、PowerPoint、图片。
- 网页内容分析。
- 视频/音频内容分析。

第一方 Skill 必须有 `origin.json`，声明所有且仅真实存在的脚本、Yunspire 所有权策略、独立实现、后台范围和隐藏 UI。校验脚本禁止引入未批准的第三方采集/解析/浏览器/语音实现，并限制 Python 为标准库、Objective-C 为 Apple 系统框架、C++ 为标准库或 Windows SDK。

### 10.4 内容去重不是来源去重

采集账本使用规范化抽取内容哈希做跨任务、跨来源去重，同时单独保存来源类型和来源引用。

- 相同内容不重复模型分析和写入。
- 新来源仍保留为来源证据。
- 已提交、写入中或已通过质量门禁的重复内容返回“跳过重复”。
- “重复跳过”不能伪装成解析失败或模型失败。

可复用经验：内容身份、来源身份和任务身份是三个不同概念，不应共用一个 ID。

### 10.5 外链图片与普通链接必须走不同策略

文件或网页中的 URL 不能一概自动访问。云枢将它们分成两类：

| 类型 | 处理方式 | 原因 |
| --- | --- | --- |
| 网页正文 `<img>`、Markdown 图片、OOXML 图片关系 | 作为媒体依赖，可在严格门禁下本地化 | 缺失会破坏原文的视觉完整性和位置表达 |
| 普通超链接 | 记录显示文字、目标和来源位置，标为 `untrusted_data`，默认 `auto_open=false`、`auto_fetch=false` | 文档内的链接本身不代表用户允许访问该地址 |

外链图片本地化的门禁包括：

1. 只接受确定图片位置中的公开 `http/https` 目标。
2. 每一跳重定向都重新解析 DNS。
3. 拒绝回环、私网、链路本地和其他非公网地址。
4. 限制重定向。
5. 校验响应 MIME 与真实图片文件签名。
6. 流式写入隔离目录并计算 SHA-256。
7. 下载、重定向、类型、哈希、暂存或原位映射失败时写入结构化原因，并阻断完整入库。

这是一条重要经验：**“自动抓取图片”是一个极窄的内容完整性豁免，不是“自动访问文档中所有链接”的授权**。

### 10.6 `asset_id` 与 `reference_id`

同一张图片可能在同一网页、Word 多处、多个 Excel 单元格或多页演示文稿中出现。只按文件哈希去重会丢失出现位置；只按位置存储又会重复分析和重复保存字节。云枢采用两层标识：

```text
原始字节 SHA-256
        ↓
asset_id      ：内容级身份，负责去重和一次模型分析
reference_id  ：位置级身份，负责原位回填和来源语义
```

每一个 `reference_id` 保留其来源：

- 网页或 Markdown 的出现顺序和文本位置。
- Word 的字符偏移、前后文或表格单元格。
- Excel 的工作表与 Drawing 锚点。
- PowerPoint 的幻灯片和元素标识。
- 文件夹导入时的来源文件稳定命名空间。

`attachment://<reference_id>` 先进入忠实 Markdown；Obsidian Adapter 最后将其映射为真实附件路径。这样可以在写入计划阶段验证“每个位置都有确切附件去向”。

### 10.7 模型视觉分析的完整性协议

模型不直接获得任意本地路径。模型分析图像时：

1. 按 `asset_id` 对相同字节只发送一次。
2. 原件不因模型分析被改写。
3. 当供应商请求边界需要时，在隔离区生成临时 JPEG 派生图。
4. 每个派生图绑定原件/派生 SHA-256、原件/派生字节数和允许的 `reference_id`。
5. 原生侧重新读取并核验实际字节和哈希。
6. 模型返回未知位置 ID 时拒绝或规范化，而不是相信其自述。
7. 前端只保留当前模型批次的派生图，提交后释放。
8. 模型结果写成 `image_observations`，再由确定性写入层展开回各个位置。

这套协议防止三个常见错误：

- 模型把观察结果挂到不存在或错误的图片位置。
- 图片在派生和写入之间被替换，导致“分析 A、保存 B”。
- 大量图片在前端堆积 Data URL，导致内存峰值随文件数量线性膨胀。

### 10.8 对话图片的视觉记忆

对话图片与采集图片走不同链路：

- 第一次进入对话时，图片由分析模型生成可持久化的摘要、OCR/画面文字、标签、实体、关键点、模型 ID 和时间。
- 普通历史上下文只带这份视觉记录，不重复发送原图或 Data URL。
- 只有用户明确按文件名、图片序号或“前两张”等表达引用历史图片时，才从当前会话原图句柄重新准备视觉输入。
- 若当前窗口已无原图句柄，系统应明确要求用户重新添加，而不是幻觉式分析。

这是一种很实用的成本与隐私优化：保存结构化视觉记忆，而不是把每张历史图像塞进每一轮上下文。

## 11. Office、网页与媒体：完整性优先于“尽量解析”

### 11.1 Office v2 的共同原则

Office 文件不是简单文本容器。若只提取段落或表格，用户会失去“图片在哪里、公式来自哪里、元素在哪一页、附属部分是否漏读”等关键信息。因此 v2 解析器将以下内容作为一等输出：

- 真实部件、关系与来源路径。
- 文本或元素的原始位置。
- 附件与图片引用。
- 完整性状态、错误和检查项。
- 可供模型分析的清洗视图与可供保真的结构 JSON。

质量策略不是“能提取多少写多少”，而是：关键 story、工作表、幻灯片、图片关系、Drawing 或位置证据不完整时，文件级错误进入采集门禁，阻断双 Vault 写入。

### 11.2 Word

Word 解析保留：

- 正文、表格。
- 页眉、页脚。
- 脚注、尾注。
- 批注。
- 分节。
- 每张图片的字符偏移、前后文、表格单元格位置和 relationship 来源。

这样模型生成的“图中内容”不会脱离原文锚点，用户也能追溯图像为什么出现在该段落旁。

### 11.3 Excel

Excel 解析先完整保留再建立清洗视图：

- 全部工作表。
- 坐标单元格。
- 普通和共享公式。
- 缓存值。
- Drawing 锚点。

处理器**不重新计算公式**。缓存值只表示文件中已有证据，不能被写成“已由云枢重新计算”。这项克制避免了没有公式引擎时产生错误结论。

质量门禁还禁止旧式 `MAX_ROWS`、`MAX_COLUMNS` 等静默截断常量。处理大表时应该分批或明确失败，而不是悄悄丢掉后半部分。

### 11.4 PowerPoint

PowerPoint 解析按 `sldIdLst` 的真实顺序，而不是按 ZIP 文件名猜测页序，并保留：

- 元素边界与层级。
- 裁剪与几何信息。
- 表格。
- 幻灯片、版式、母版来源。
- 图片关系和元素标识。

空间关系被明确标记为“非语义事实候选”：它可以帮助模型理解布局，但不能因为两个元素距离近就断言业务关系。

### 11.5 PDF、图像、音视频的跨平台实现

| 平台 | PDF/图像 | 媒体/语音 | 设计要点 |
| --- | --- | --- | --- |
| macOS | PDFKit、ImageIO 等系统框架 | AVFoundation、Speech | 使用系统已提供的能力；解析/渲染失败形成明确状态 |
| Windows | Windows.Data.Pdf、WIC | Media Foundation、SAPI | 用 C++ 原生辅助程序处理平台 API 和 Unicode 路径 |

Windows 媒体辅助程序使用 Media Foundation 读取媒体、进行帧差和候选间隔计算、生成 PCM 音频；SAPI 根据语言匹配可用识别器。缺少目标语言离线识别器时返回 `windows_sapi_language_unavailable` 或等价明确错误，不悄悄换成错误语言。

### 11.6 网页与 HLS/媒体的资源策略

网页抽取不再按固定图片数量或固定正文字符数静默截断。视频/HLS 对象流式落盘，不把全部对象载入内存。与本地上传同理，限制来自实时资源和供应商请求边界，而不是人为“文件不能超过某大小”的产品规则。

## 12. 双 Vault 提交：将来源保真与模型理解分离

### 12.1 为什么不能只保存一份“AI 整理后的笔记”

只保存模型改写稿会丢掉来源，无法审计；只保存原文则无法形成有用的知识关联。云枢把两者作为同一采集批次的关联交付物：

| 目标 | 内容 | 不能做什么 |
| --- | --- | --- |
| 用户指定 Vault，默认个人库 | 忠实 Markdown、原位附件、来源证据 | 不能被模型摘要或改写替代 |
| Agent 库 | 结构化理解稿、逐图分析、标签、Wiki Links、相关笔记 | 不能冒充原始来源文件 |

两份内容复用同一模型分析回执，但文件责任清晰，避免“看起来像原文但其实已被模型重写”的知识污染。

### 12.2 稳定命名与不可覆盖

文件和附件采用“完整内容 SHA-256 目录 + 可读标题文件名”的稳定目标路径：

- 同标题、不同内容不会碰撞。
- 同内容可定位为同一内容身份。
- 采集批次拒绝覆盖已有目标。
- 目录或文件名变化不会依赖模型随机生成的短 ID。

这种布局保留可重现、可去重、可审计的落盘语义，同时让 Obsidian Graph 以可读 basename 展示节点，而不是显示整段哈希。

### 12.3 批量提交与补偿回滚协议

提交前需要完成：

1. 生成两个 Vault 的写入计划。
2. 规范化并检查目标相对路径。
3. 校验附件暂存 claim、哈希和 `reference_id` 映射。
4. 检查目标冲突、外部变更和不能覆盖的已有文件。
5. 在批次检查点目录为每一个已有目标保存写前副本，并记录哪些目标原本不存在。
6. 每个文件分别使用同目录临时文件、刷新和原子替换。
7. 同步写入失败时按已提交数量恢复副本；操作事件写入失败时恢复整个批次。
8. 成功后更新索引、任务、操作事件和对话结果。

任一必需附件、图片本地化、Office 完整性或一个 Vault 的写入失败，都不能返回“完整成功”。这把“跨两个存储边界的逻辑事务”从用户感知层做成全有或明显失败。

**当前风险/缺口**：这不是操作系统级跨目录事务。实现会顺序写多个文件，并对已观察到的错误执行补偿回滚；如果进程或机器恰好在两个文件写入之间崩溃，当前源码没有可证实的批次 manifest、提交进度 fsync 和启动自动回滚/补提交流程。检查点文件会保留证据，但仍需要人工或后续恢复器处理。因此对外应称“带补偿回滚的逻辑批次”，不应把它等同于崩溃原子的数据库事务。

### 12.4 外部编辑与冲突

Obsidian 是用户可直接编辑的文件系统，不是应用私有数据库。适配器因此需要：

- 写入前比较版本或哈希。
- 发现外部修改时停止覆盖。
- 监听外部文件变化。
- 增量重建索引。
- 让 Vault 外部修改优先于缓存。

可复用经验：当用户拥有权威文件时，缓存只能加速，绝不能反客为主。

## 13. SQLite 运行时：可恢复状态而非临时 UI 数据

### 13.1 当前数据库能力

`runtime_db.rs` 的当前 schema 版本为 21。数据库保存：

- 工作区状态与快照。
- Vault 注册。
- 模型供应商与加密凭据。
- 会话、消息与图片记忆。
- 应用命令、策略决策与审批；已接受命令的 payload 可保留其回执标识作为审计证据。
- 任务、步骤、检查点、计划与报告订阅。
- 采集记录、内容去重账本、受管资源。
- 模型请求与用量。
- 操作事件。
- FTS。
- 长期记忆投递状态和优化记录。
- 迁移版本、备份和恢复信息。

实时的一次性意图/分析回执是有界、带 TTL 的原生内存状态，不是 SQLite 可恢复授权。应用重启会主动让未完成的短期模型授权失效；数据库保存的是已经提交的命令、策略、任务和事件事实。

### 13.2 可靠性设置

打开数据库时设置：

```sql
PRAGMA journal_mode=WAL;
PRAGMA synchronous=FULL;
PRAGMA foreign_keys=ON;
PRAGMA temp_store=MEMORY;
```

此外使用：

- 版本化迁移。
- `PRAGMA integrity_check`。
- 在线备份 API。
- 受限备份目录和路径校验。
- 恢复前预检。
- 恢复前再次建立当前状态安全备份。
- 恢复后重新迁移、检查完整性和 WAL checkpoint。

### 13.3 事务、幂等与事件

受 `ApplicationCommand` 管理的任务转换和部分 Vault/采集提交使用稳定幂等键，避免“重启后重复执行”或“补跑时重复写入”，并带 trace ID 或写入 append-only 的 `operation_events`。

**当前风险/缺口**：模型供应商保存、连接器保存/删除等直接 Tauri handler 不接收 trace ID，也没有可证实的 `OperationEvent`。因此“每个副作用都有 trace 和事件”仍是目标，而非当前全覆盖事实；应与 6.4 的 effectful handler 票据一起补齐。

在工程上，建议把以下动作放在同一个事务边界或至少同一个可恢复工作流中：

```text
状态转换
→ 资源提交/回执写入
→ 操作事件
```

否则很容易出现“UI 显示成功、文件已写入、但数据库无事件”或反过来的断裂状态。

### 13.4 长期记忆与后台优化

长期记忆采用追加式事件结构，写入分三步：暂存、Vault 原子写入、数据库提交。崩溃后可重放未完成事件。

治理能力包含：

- 查询与指标。
- 用户纠正。
- 过期。
- 替代。
- 墓碑。
- 不可变证据游标。
- 后台优化候选。
- 权限扩张检查与确定性评估。
- 用户审阅后才成为新版本。

不得进入长期记忆的数据包括密钥、Cookie、令牌、完整二进制附件和无关系统隐私。

这里的经验是：长期记忆不是“把聊天记录永久塞进上下文”，而是一套有来源、纠正、淘汰、审阅和回滚语义的数据产品。

### 13.5 定时任务和报告

用户用自然语言表达周期、时区、来源、目标和失败策略；模型负责理解，调度器负责保存确定计划、领取到期任务、控制重叠、补跑、重试和幂等。

日报、周报、月报和年报先写入 Obsidian。没有配置外部连接器时，仅进入本地待投递状态。这样“生成报告”和“向外部发送报告”不会因为同一条自然语言而被合并成不可逆动作。

## 14. 安全边界、连接器与更新恢复

### 14.1 威胁模型的核心原则

云枢将用户内容、网页、文件、图片、音视频和模型输出统一视为不可信数据。这个判断贯穿：

- 不把外部内容嵌入系统提示词作为指令。
- 不把模型自由文本当作可执行命令。
- 不允许助手改设置。
- 不允许内容决定目标路径、能力、域名或预算。
- 不允许普通链接因解析而自动访问。
- 不把凭据写入 Vault、记忆、日志或仓库。

### 14.2 路径和文件系统边界

原生层负责：相对路径规范化、越界拒绝、冲突检查、同目录原子替换、检查点、软删除到回收区、显式用户动作才进行物理删除。更新快照和回滚不跟随符号链接。

### 14.3 外部连接器

外部连接器只能由用户在设置中创建，配置地址必须是规范化 HTTPS 目标，凭据加密保存。AI 助手可以在模型确认正文和连接器类型后提出候选投递，但 Policy Engine 仍将投递视为高风险副作用并要求用户确认。

**当前风险/缺口**：采集图片本地化会逐跳拒绝非公网 IP；当前连接器验证强调干净 HTTPS 与禁止重定向，但不能据此证明对公网 IP 的同等强度校验。后续应统一复用 DNS 解析、地址分类、连接地址钉扎和每跳复查逻辑，防止连接器成为较弱的 SSRF 面。

### 14.4 更新保护与回滚

更新模块当前只检查项目 GitHub 仓库的稳定 Release。安装前：

1. 创建 SQLite 在线备份。
2. 为所有已连接 Vault 创建文件快照。
3. 校验路径边界并拒绝符号链接跟随。

回滚前会再建当前状态安全点，然后只覆盖旧快照中存在的文件，不删除更新之后新增的文件。这样可降低“回滚删除用户在更新后新增内容”的风险。

**明确延期**：当前不包含自动下载/安装、Apple 代码签名或公证。

### 14.5 发布边界

源码发布包禁止包含：Vault、`.obsidian/`、SQLite 数据库、设备密钥、日志、缓存、检查点、备份、截图、构建产物、`node_modules/`、`dist/`、Rust `target/` 和本机绝对路径。

这不仅是清洁度问题，也是防止隐私泄露、意外二进制提交和“我的机器能运行”伪证据进入发布包的问题。

## 15. 跨平台构建与 Windows 交付

### 15.1 环境基线

| 环境 | 要求 |
| --- | --- |
| macOS | macOS 13+、Xcode Command Line Tools / Apple clang |
| Windows | Windows 10/11 x64、Visual Studio 2022 Build Tools、MSVC x64、Windows SDK |

### 15.2 Windows 嵌入式 Python

Windows 包将 Python 3.13.7 x64 嵌入式运行时作为受控资源：

1. 从 Python.org 官方地址下载。
2. 核验固定 SHA-256。
3. 核验官方 MD5。
4. 写入运行时清单。
5. 配置 `python313._pth`。
6. 冒烟验证解释器和随包解析器。

使用嵌入式运行时的目的是让 Office/网页解析不依赖用户另行安装 Python，同时把供应链校验纳入构建过程。

### 15.3 Windows 安装验证

当前 Windows workflow 配置声明以下步骤：

```text
发布审计
→ npm ci
→ 构建 Python 与原生辅助程序
→ 完整工程验证
→ 核验运行时与辅助程序
→ 构建未签名 x64 NSIS
→ 安装后核验资源、Unicode PDF、媒体、语音和校验和
```

产物作为短期保留的未签名安装包上传。其优点是对“压缩包构建成功”之外的安装后资源问题有覆盖。

### 15.4 当前交付缺口

- 没有可证实的 macOS 签名、公证、DMG 分发或 Release 发布工作流。
- Windows 包是未签名 NSIS，部署到终端环境仍会遇到信任提示。
- GitHub Actions 验证的是构建与安装冒烟，不等于真实用户 Vault、模型供应商和外部网络的端到端验收。

## 16. 开发问题台账：问题、根因、解法与防复发机制

下表只记录能由现有设计、源码或质量检查支持的问题类型。它不声称每一项都有独立的线上事故记录。

| 编号 | 问题或风险 | 根因 | 采用的办法 | 防复发机制 |
| --- | --- | --- | --- | --- |
| P01 | 模型文字可能诱导系统执行副作用 | 将自然语言当作命令会混淆数据、指令和授权 | 候选意图 + 能力目录 + `ApplicationCommand` | Policy 单元测试；命令结构化校验 |
| P02 | 前端可伪造“模型已决定执行” | UI 与模型输出都不能被当作信任根 | 一次性模型意图回执，由 Command Bus 消费 | 回执缺失直接拒绝；重放不可用 |
| P03 | 助手可能修改安全设置 | 助手意图与用户直接操作混在同一接口 | 按 `CommandOrigin` 区分；助手设置写入拒绝 | Policy 测试覆盖助手拒绝、直接用户允许 |
| P04 | 删除或外部发送被普通写入路径放行 | 副作用风险不同 | 按操作分类返回 `require_approval`，写入建检查点 | 状态机和确认 UI；操作事件 |
| P05 | 路径穿越或绝对路径写入 | 文件系统参数来自 UI、模型或导入内容 | 相对路径规范化，拒绝空路径、绝对路径、`.`、`..`、NUL | Policy 单元测试；Adapter 边界二次校验 |
| P06 | 长任务重启后丢状态或重复执行 | 把任务状态留在前端内存 | SQLite 持久任务、检查点、幂等键、合法状态机 | 终态不可重启；迁移和任务测试 |
| P07 | UI 报成功但文件或数据库未完整提交 | 多个存储动作没有共同完成语义 | 写入计划、单文件原子替换、双 Vault 预检、补偿回滚、事件记录 | 已观察错误时不生成成功回执；崩溃窗口另见 P28 |
| P08 | 用户原文被模型摘要覆盖 | 将“知识整理”与“来源保存”混为一层 | 忠实层与理解层双 Vault 交付 | 不同目标目录和内容责任；写入计划校验 |
| P09 | 大文件 IPC 内存峰值失控 | 一次性读取和传递整个文件 | 分块上传、流式暂存、流式哈希和复制 | 质量门禁检查前端 `file.slice()` 与原生命令注册 |
| P10 | 无上限需求被错误实现成无限模型请求 | 文件大小和请求大小是不同概念 | 文件可流式接收；模型正文/图像按字节批处理和汇总 | 检查禁止旧 4 MB 静默截断；检查批处理原语 |
| P11 | 图片去重导致原位语义丢失 | 内容身份与位置身份混用 | `asset_id` 去重、`reference_id` 记录每次出现 | 模型绑定和附件映射的结构化校验 |
| P12 | 模型给图片观察挂错位置 | 模型输出中的标识不可信 | 派生图绑定允许的 `reference_id`，原生侧核验 | 未绑定位置拒绝/规范化；哈希核验 |
| P13 | 历史对话重复发送原始图片 | 直接把附件 Data URL 放进每轮上下文 | 首次图像建立持久视觉记忆；按明确引用才重取原图 | 质量门禁扫描普通附件上下文不得写 Data URL |
| P14 | 文档图片自动下载成为 SSRF 入口 | 把 URL 当作可直接访问的资源 | 公网地址、逐跳 DNS、重定向、MIME/签名、隔离落盘 | 采集器和质量门禁检查网络约束 |
| P15 | 普通链接被解析器意外访问 | “出现 URL”被误解为“用户许可访问” | 普通链接只记录为不可信数据 | 只有明确用户命令创建新的采集任务 |
| P16 | Office 文本提取成功但结构/图片位置丢失 | 仅按纯文本提取，忽略 OOXML 关系 | Word/Excel/PPT v2 结构、位置、关系和完整性输出 | 关键部件缺失阻断双库写入；质量门禁检查 v2 原语 |
| P17 | Excel 公式值被误导为已计算结果 | 解析器没有公式计算引擎 | 保留公式与缓存值，明确不重算 | 文档契约和解析结果字段区分证据 |
| P18 | 网页、图片或表格被静默截断 | 固定大小/数量上限隐藏数据损失 | 流式处理、分批、分层汇总或明确错误 | 质量门禁搜索旧 `slice`、行列和图片数量限制 |
| P19 | Vault 外部修改被缓存覆盖 | 将应用内索引误作权威 | 写入前冲突检查，文件监听和增量重建 | Vault 外部修改优先原则写入架构与适配器 |
| P20 | SQLite 崩溃或恢复导致数据不一致 | 默认数据库设置和恢复流程不足 | WAL、FULL 同步、外键、迁移、完整性检查、在线备份 | 恢复预检、安全备份、恢复后检查 |
| P21 | 凭据泄露到 Markdown、日志、仓库或同用户本机进程 | 配置与知识/审计数据无隔离；密钥文件与数据库同目录 | AES-256-GCM + scoped AAD；Unix key 文件 `0600`；敏感字段过滤；发布审计 | 仍需 macOS Keychain/Windows DPAPI 或等价系统密钥保护 |
| P22 | 更新失败或回滚删除新文件 | 没有更新前保护点，或简单目录覆盖 | SQLite/Vault 保护点；回滚只覆盖旧快照已有文件 | 路径边界、符号链接限制、回滚前安全点 |
| P23 | 跨平台辅助资源在安装后丢失 | 仅验证编译输出，不验证安装包 | Windows workflow 配置构建 NSIS 后安装并检查资源和 Unicode 冒烟 | `verify-windows-release.mjs` 生成检查和校验和；仍需真实 Actions run 证据 |
| P24 | 第一方 Skill 被无意替换为外部实现 | 脚本目录、来源和依赖没有约束 | `origin.json` 完整声明；语言/框架依赖白名单 | `validate-first-party-skills.mjs` |
| P25 | UI 细节和安全约束在重构中退化 | 传统单测难覆盖 DOM/CSS/调用模式 | 源码级质量门禁 | 对关键字符串、结构、无障碍和禁用旧模式做断言 |
| P26 | 连接器可能弱化网络安全边界 | 采集和投递各自实现网络验证 | 当前已有 HTTPS/无重定向校验 | 后续统一 SSRF 防护库并做回归测试 |
| P27 | “所有副作用走 Command Bus”未对每个 IPC 机械强制 | 授权后仍有专用 effectful Tauri handler，各模块分别校验 | 当前使用应用授权、prepare/commit ID、路径/哈希/确认等局部门禁 | 引入能力范围执行票据和 effectful handler 覆盖表 |
| P29 | Token/成本预算字段看似存在但没有硬上限 | `max_tokens` 未在 Policy 校验；`max_cost` 只校验数值合法性 | 步骤、工具和运行时间已有上限；模型用量另有账本 | 增加按任务累计 Token/成本的执行前后门禁和超限取消 |
| P30 | `allow_with_reduced_scope` 容易被误报为已实现 | 枚举和数据库接受该值，但 evaluate 无返回分支 | 当前实际只返回 allow/deny/require_approval | 实现规范化降权、参数重写、用户展示和单元测试，或移除预留值 |

### 16.1 这些问题如何改变开发方法

问题台账显示，最有效的改法不是修一个分支，而是把问题上升成系统不变量：

| 局部问题 | 升级后的不变量 |
| --- | --- |
| “别让模型误删文件” | 模型输出永远不是授权；删除必经策略、审批、检查点和审计 |
| “别丢 Office 图片” | 关键结构不完整时不能形成成功入库 |
| “别卡死大文件” | 文件流、模型流和存储流分别有界，而非一个万能大小常量 |
| “别重复分析图像” | 内容身份与位置身份永远分离 |
| “别污染用户原文” | 来源忠实层与模型理解层不可混写 |
| “别让修复又退化” | 把约束写成自动化门禁，而不是留在口头经验中 |

| 协议层 | `scripts/validate-schemas.mjs` | 任务、计划、入站内容、记忆、Skill 等 JSON Schema |
| 来源层 | `scripts/validate-first-party-skills.mjs` | Skill 来源声明、脚本清单、依赖限制、后台隐藏性 |
| 发布边界 | `scripts/audit-release.mjs` | 必需文件、版本一致性、指定双语文档、禁止本机路径/密钥/产物 |
| 产品约束 | `scripts/quality-gates.mjs` | UI、无障碍、上传、图片、Office、网络、模型批处理、Windows 资源等 |
| Rust 静态质量 | `cargo fmt --check`、`cargo clippy -D warnings` | 格式和警告零容忍 |
| Rust 行为 | `cargo test --all-targets` | 策略、状态机、数据库、采集、模型、Vault、连接器、更新等模块行为 |
| 桌面构建 | `vite build`、Tauri Debug 构建 | 前端产物与原生应用打包 |
| 安装验证 | Windows NSIS 安装后检查 | 资源存在、Unicode 路径、PDF、媒体、语音、校验和 |

### 17.2 `quality-gates.mjs` 的独特价值

它不是一般 lint，而是将过去容易回退的产品约束写成源码检查。例如：

- CSP 必须默认 `self`，不允许 inline script。
- HTML 需中文语言标记、live region、模态语义和破坏性确认锁。
- 必须正好十个导航路由和页面视图。
- 页面与任务抽屉必须有独立滚动/固定覆盖层。
- 首次引导必须刚好五步，头像选择不能少于规定集合。
- 分块上传的三个前端调用和三个原生命令必须同时存在。
- 失败路径必须释放暂存附件，启动必须清理遗留暂存。
- 禁止旧 128 MB 附件总量拒绝、旧 4 MB 分析截断、固定视频/媒体/HLS 上限。
- 普通对话历史不得重复放入图片 Data URL。
- Office v2、Windows PDF/WIC/Media Foundation/SAPI、嵌入式 Python 校验原语必须存在。
- 禁止 Excel 固定行列截断、网页固定图片数/正文截断、嵌入链接固定数量截断。
- 前端每个原生 `invoke` 必须在 Tauri handler 注册，HTML 图片必须提供 `alt`。
- 构建产物必须存在，且单个 JavaScript 不超过 2 MiB、单个 CSS 不超过 768 KiB、总产物不超过 12 MiB。

可复用经验：当 bug 的本质是“某段实现绝不能再出现”，源码模式门禁比依赖人工记忆更有效。但它应与行为测试配套，不能成为唯一验证方式。

### 17.3 CI 流程

`ci.yml` 在 macOS 与 Windows 矩阵中执行相同的完整产品门禁：

```text
checkout
→ Node 22
→ Rust 1.88 + rustfmt + clippy
→ npm ci
→ npm run verify
→ Windows 源资源附加校验
```

`windows-installer.yml` 在主分支、Pull Request 或手动运行时验证 Windows 安装链：

```text
checkout
→ Node 22
→ Rust 1.88 MSVC
→ npm ci
→ npm run verify
→ 辅助程序核验
→ 未签名 NSIS 构建
→ 安装后验证与产物上传
```

`release.yml` 只在匹配版本标签或手动发布时运行。它先验证版本、标签和发布源，再分别构建 macOS 通用 DMG 与 Windows x64 NSIS；两个平台都通过后才允许发布 GitHub Release。工作流配置本身不是通过证明，只有对应提交的 Actions 运行记录和产物摘要才是远端证据。

### 17.4 已有验证证据与本次文档验证边界

验证证据必须绑定到当前提交、实际命令、工具版本和退出状态。文档不得保留已经失效的工作区哈希、历史测试数量或旧版本审计输出，也不得把 workflow 配置当成运行通过。正式发布还需记录安装包文件名、字节数、SHA-256、签名状态、目标平台和来源提交。

### 17.5 推荐的本地验证顺序

```bash
npm ci
npm run verify
node scripts/verify-release-artifact.mjs source --tag v0.1.2 --require-windows true
git diff --check

# 当前平台桌面冒烟包
npm run tauri:build:debug
```

`npm run verify` 已统一执行发布审计、Schema、第一方 Skill、前端回归测试、构建、产品质量门禁、Rust 格式、Clippy 和全部原生测试。出现失败时仍需记录具体子命令、错误和环境；发布安装包还必须在对应目标平台执行安装后验证。

### 17.6 这些验证不能证明什么

- `quality-gates.mjs` 大量使用 `includes`、正则和固定字符串，它能发现已知实现退化，但不能单独证明运行时行为正确；函数改名或无行为变化的重构也可能触发它。
- 发布审计对列出的二进制扩展不做文本扫描，也跳过大于 5 MiB 的文件；它不是完整 DLP。
- 双语检查只验证指定文档有中英文标题，不证明两种语言语义等价。
- 版本检查覆盖发布清单中的明确文件；新增平台资源时必须同步扩展清单。
- 当前流程未提供依赖漏洞扫描、SBOM、许可证兼容自动检查或产物签名验证。
- 即使按当前 macOS/Windows workflow 配置完成构建和冒烟，也不能证明真实模型供应商、真实用户 Vault 和复杂网络环境的完整端到端正确性。
- 发布审计扫描本机路径、密钥、生成产物、嵌套仓库和版本一致性，但仍不是完整 DLP、依赖许可证审查或第三方源码相似度证明。

## 18. 开发过程的优势、取舍与边界

### 18.1 已形成的工程优势

1. **权限模型先于智能能力**：把“模型会做什么”与“系统允许做什么”拆开，抗提示注入和 UI 伪造能力更强。
2. **本地权威清晰**：Vault 与 SQLite 的职责不会互相竞争；索引可以重建。
3. **来源可审计**：忠实层、理解层、来源证据、位置引用和内容哈希共同保留。
4. **完整性标准高**：关键图片、Office 关系和双 Vault 写入失败时不伪报成功。
5. **面向失败设计**：任务状态、检查点、幂等、备份、恢复、回滚和操作事件不是事后补丁。
6. **跨平台不是只编译**：Windows 继续验证安装包里的原生资源、Python、PDF、图像、媒体和语音。
7. **质量规则可执行**：架构约束被转成 schema、单测、源码模式门禁、workflow 配置和发布审计。
8. **开发透明度较高**：架构、PRD、AI 合同、贡献说明、变更记录、安全说明和协作模板都在仓库内。

### 18.2 有意识的取舍

| 取舍 | 得到什么 | 付出什么 |
| --- | --- | --- |
| 模块化单体而非多 Agent | 统一状态、权限、事务和审计 | 核心文件变大，模块边界需持续维护 |
| 原始数据与理解数据双写 | 可追溯且可用 | 写入计划、冲突处理、事务感知更复杂 |
| 不设产品级文件大小上限 | 不人为排除大型知识来源 | 必须投入流式、资源门禁、批量和失败恢复 |
| 使用系统框架而非大型第三方工具 | 第一方实现可审计、包体更可控 | 平台差异和原生辅助程序维护成本增加 |
| 静态质量门禁 | 防止已知回归 | 字符串/结构检查会脆弱，需与行为测试平衡 |
| 不实现自动更新安装 | 避免未签名环境下高风险自动替换 | 用户仍要处理下载、签名和分发流程 |

### 18.3 已经避免的错误做法

质量门禁显示项目主动避免了以下短期省事、长期危险的实现：

- 用前端硬编码演示状态替代真实任务和持久化。
- 直接执行模型回复或由模型自行设置权限。
- 用固定 4 MB、128 MB、固定行列或固定图片数量做静默截断。
- 将所有图片先转 Data URL 再统一发送。
- 用摘要覆盖原文，或让理解稿伪装成来源。
- 在检测到关键附件/Office 关系不完整时仍写“成功”。
- 自动访问文件内所有 URL。
- 把第三方爬虫、解析器或语音模型直接塞进第一方 Skill。
- 只打包，不实际安装并验证 Windows 资源。
- 把 Vault、数据库、密钥、日志或构建物混进源码发布。

## 19. 可复用开发方法：从需求到可验证交付

以下流程适用于本地优先 AI 桌面、知识管理、自动化和带副作用的 Agent 类产品。

### 19.1 第一步：写出权威与非目标

在写 UI 前回答：

1. 用户可直接拥有和修改的权威数据是什么？
2. 哪些是运行状态，哪些是可重建索引？
3. 模型能提出什么，绝不能决定什么？
4. 哪些功能必须明确延期？

产物应至少包括：架构边界文档、产品非目标清单、数据分类表、敏感数据清单。

### 19.2 第二步：为副作用建立统一命令路径

不要为每个按钮或每个模型工具单独拼权限判断。建立：

```text
用户/模型输入
→ 类型化命令
→ 确定性策略
→ 审批/降权
→ 持久任务
→ 能力执行
→ 事件与结果
```

命令字段应至少有：来源、能力、操作、目标、范围、预算、幂等键、trace ID、模型证据。策略必须可独立单测。

### 19.3 第三步：先设计失败和恢复

针对每类副作用，先回答：

- 写到一半崩溃怎么办？
- 用户取消怎么办？
- 重试会不会重复写？
- 外部文件变化怎么办？
- 成功的最小证据是什么？
- 如何从检查点恢复？

然后再写 happy path。云枢中的检查点、状态机、幂等键、原子写、备份与回滚均由这个问题集导出。

### 19.4 第四步：把大对象做成流，而非大变量

分别为三条流设计界限：

| 流 | 正确边界 |
| --- | --- |
| 用户文件 → 应用 | 分块、暂存、累计字节和流式哈希 |
| 应用 → 模型 | 上下文/请求字节边界、批处理、汇总、图像临时派生 |
| 应用 → 持久存储 | 原子文件写、事务、附件 claim、冲突检查和清理 |

“没有产品级大小上限”只能意味着用户输入不被任意拒绝，不能取消运行时资源限制。

### 19.5 第五步：按数据责任拆分模型产物

模型生成的任何产物至少问两个问题：

1. 它是否应替代用户原件？通常答案是否。
2. 它是否需要回到原件的确切位置？若需要，必须保存位置级标识。

由此可导出忠实层/理解层、`asset_id`/`reference_id`、模型输入 binding 和结构化观察，而不只是“把模型文本保存成笔记”。

### 19.6 第六步：让不可退化的规则自动失败

将关键不变量分层编码：

- 协议结构：Schema。
- 决策逻辑：单元测试。
- 文件/数据库语义：集成测试与恢复测试。
- 易回退源码模式：质量门禁。
- 发布内容：审计脚本。
- 平台资源：安装后冒烟测试。

好的质量门禁描述的是“为什么不允许”，而不是只检查某段代码文本。

### 19.7 第七步：把用户可见的状态锚定在事实

页面上的“已完成、已保存、已取消、待确认、已跳过重复”必须来自任务、回执、文件提交或操作事件。模型措辞只能是解释，不是状态来源。

## 20. 可复制检查清单

### 20.1 需求与架构检查

- [ ] 写出产品目标、明确延期范围和不可绕过的系统约束。
- [ ] 标注每类数据的权威来源、生命周期和是否可重建。
- [ ] 明确模型输出是候选数据还是授权证据；禁止二者默认等同。
- [ ] 画出从用户输入到副作用、提交和审计事件的完整链路。
- [ ] 为删除、外部投递、设置修改、更新和恢复分别定义风险等级。
- [ ] 列出外部内容、模型输出、文件路径、URL、图片和凭据的信任等级。
- [ ] 确认前端、原生层、适配器和持久层各自不能做什么。

### 20.2 命令、策略和任务检查

- [ ] 所有副作用都有结构化命令，而不是执行自由文本。
- [ ] 命令含来源、能力、操作、参数、目标、范围、预算、幂等键和 trace ID。
- [ ] 助手来源的执行命令必须携带短期一次性意图回执。
- [ ] 回执绑定工作区/能力/用户输入，并在消费后失效。
- [ ] Policy Engine 独立于模型，可单测 `allow/deny/require_approval/reduced_scope`。
- [ ] 路径拒绝绝对路径、空段、`.`、`..`、NUL 和符号链接越界。
- [ ] 网络目标有协议、域名、重定向、DNS 和地址类别策略。
- [ ] 预算有步骤、工具、时长、Token 和成本上限。
- [ ] 状态迁移由状态机验证；终态不可重启。
- [ ] 取消、暂停、恢复、重试都生成真实事件和可追踪结果。

### 20.3 大文件与媒体检查

- [ ] 文件通过分块 IPC 和隔离暂存，不通过一个大 Data URL。
- [ ] 完成上传时验证声明字节数、实际字节数和 SHA-256。
- [ ] 失败路径释放暂存；启动时清理过期暂存。
- [ ] 产品输入大小、单次 IPC 大小、模型请求大小和资源预算分别定义。
- [ ] 文本按 UTF-8 字节而不是仅按字符批处理。
- [ ] 批次结果有层级汇总，不静默丢弃后半部分。
- [ ] 图片分析只对内容级资产去重，对每次出现保留位置引用。
- [ ] 派生图绑定原件哈希、派生哈希、字节数和允许位置。
- [ ] 原件在模型分析期间变化时阻断继续提交。
- [ ] 媒体和 PDF 的平台辅助程序有安装后冒烟测试。

### 20.4 Office 与网页内容检查

- [ ] Office 解析输出原始部件/关系、清洗视图和完整性状态。
- [ ] Word 保留 story、图片字符位置和表格上下文。
- [ ] Excel 保留工作表、坐标、公式、缓存值和 Drawing 锚点；不伪装重算。
- [ ] PowerPoint 按真实页序保留元素、层级、几何、版式和母版来源。
- [ ] 必需结构缺失会阻断入库，不能以部分成功掩盖。
- [ ] 普通链接默认不访问；图片依赖仅走窄范围本地化器。
- [ ] 本地化器逐跳检查 DNS、私网/回环、重定向、MIME 和文件签名。
- [ ] 外链失败保留结构化原因和来源位置。

### 20.5 双 Vault 与文件系统检查

- [ ] 来源忠实层与模型理解层有不同目标和明确命名。
- [ ] 文件和附件使用完整内容哈希目录、可读标题文件名和不可覆盖策略。
- [ ] 每个附件位置能解析到唯一 `reference_id` 和最终路径。
- [ ] 写入前检查外部修改、目标冲突和路径范围。
- [ ] 使用同目录临时文件、刷新和原子替换。
- [ ] 双库任一必需写入失败时不返回完整成功。
- [ ] 删除先进入回收区，永久删除必须是明确用户动作。
- [ ] 外部文件变化可触发增量索引重建。

### 20.6 数据库、记忆和更新检查

- [ ] SQLite 启用 WAL、FULL 同步、外键并有版本化迁移。
- [ ] 启动或健康检查执行完整性检查。
- [ ] 状态、资源回执和操作事件有事务或可恢复工作流关联。
- [ ] 长期记忆采用追加式事件，支持纠正、过期、替代和墓碑。
- [ ] 记忆不存密钥、Cookie、令牌和无关二进制附件。
- [ ] 更新前同时保护 SQLite 与所有连接 Vault。
- [ ] 恢复前建立当前安全点，回滚不删除更新后新增文件。
- [ ] 备份和恢复路径拒绝符号链接和越界路径。

### 20.7 前端和无障碍检查

- [ ] 路由和页面一一对应；没有“导航存在但页面不存在”。
- [ ] 长内容独立滚动；任务抽屉不挤压主工作区。
- [ ] 模态框、live region、键盘焦点和破坏性确认语义完整。
- [ ] 真实任务和真实结果驱动 UI，不预填演示数据。
- [ ] 图片头像、名称、语言和风格来自持久化偏好，不硬编码。
- [ ] 普通历史不重复发送原始图像 Data URL。
- [ ] 设置入口只属于用户，助手不能替用户改配置。

### 20.8 发布与协作检查

- [ ] 纯净源码目录先通过发布审计，再安装依赖。
- [ ] 版本字段在 package、Cargo、Tauri、UI 和资源清单中一致。
- [ ] 不提交 Vault、数据库、密钥、日志、缓存、备份、截图和构建产物。
- [ ] Schema、第一方 Skill、前端质量、Rust fmt/Clippy/测试全部有命令证据。
- [ ] CI 版本和本地验证版本一致，并明确未验证的部分。
- [ ] Pull Request 写目标、数据/权限影响、风险、验证和回滚。
- [ ] Issue 只提交脱敏、最小复现和相对路径证据。
- [ ] 双语公开文档和版本字段同步更新。

## 21. 当前技术债与下一迭代优先级

### 21.1 P0：交付可信度

1. 为所有 effectful Tauri handler 引入能力范围执行票据，机械证明策略、任务、审批与最终提交之间的绑定。
2. 为跨 Vault 批次增加持久 manifest、提交进度 fsync、启动恢复器和故障注入测试。
3. 将 `desktop/` 当前 Windows/安全快照纳入正式可达 Git 历史，明确提交边界和发布分支。
4. 建立 macOS 签名、公证、产物校验和正式 Release 发布流程。
5. 在 CI 或受控环境补充真实 Tauri 运行冒烟：应用启动、授权、Vault 发现、模型配置、最小采集和任务回传。
6. 对连接器复用采集链的公网地址校验，增加 DNS 重绑定、重定向和私网地址测试。
7. 用 macOS Keychain、Windows DPAPI 或等价系统设施保护设备密钥，并设计已有 key 文件的安全迁移。
8. 增加依赖漏洞扫描、SBOM、许可证检查和签名后产物验证。

### 21.2 P1：可维护性与测试

1. 将 `desktop-ui/app.js` 按助手、采集、模型、任务、设置、创作、报告、渲染和状态存储拆为 ES modules。
2. 将 `runtime_db.rs` 按 schema/migration、会话、任务、模型、记忆、备份和事件拆分，保留事务边界。
3. 将 `obsidian.rs` 的 Vault I/O、索引、附件、冲突、回收和回执拆分。
4. 为分块上传、跨批次模型汇总、双 Vault 部分失败、恢复重放、图片绑定和 Office 完整性补充 fixture 测试。
5. 增加 Windows 与 macOS 的真实 Unicode、超大文件、外部编辑冲突和磁盘不足测试。
6. 为 Token/成本做任务级累计、执行前预算和超限取消；为降权结果增加真实参数缩减分支和测试。

### 21.3 P2：产品能力与性能

1. 对模型、解析器、写入和网络流增加统一的预算/背压/取消接口。
2. 让 UI 从原生事件流订阅任务，而不是依赖轮询或本地推断。
3. 增加采集账本、图片资产和模型用量的可视化诊断，但不泄露敏感数据。
4. 已在 FTS 上加入确定性本地特征向量与标准 RRF，并保持缺失/损坏向量时的 FTS 回退；实体图谱、神经 Embedding 和学习式语义重排仍需在有明确需求与评估集后再设计。

### 21.4 P3：生态和运维

1. 提供经过审计的导出/迁移工具，明确设备密钥不可迁移时的重新配置路径。
2. 建立灾难恢复手册：数据库损坏、Vault 冲突、模型供应商不可用、磁盘不足、更新失败。
3. 为连接器、更新、长期记忆优化和第一方 Skill 建立变更兼容性矩阵。

## 23. 结论：最值得复用的十条经验

1. 先定义权威边界，再定义功能；先定义非目标，再定义路线图。
2. 把模型输出当候选数据，把确定性策略当授权来源。
3. 用一次性、可过期、不可重放的意图回执连接“模型理解”和“允许执行”。
4. 统一副作用路径：命令、策略、任务、能力、提交、审计必须可追踪。
5. 大输入设计成流和批次，不用任意静默截断掩盖资源问题。
6. 内容身份、来源身份、任务身份和位置身份不能混用。
7. 来源保真与模型理解要分开交付，尤其是用户拥有的知识文件。
8. 完整性要求必须是阻断门禁，而不是日志里的警告。
9. 数据库、Vault、索引、更新和回滚要在第一天一起设计。
10. 把容易退化的产品原则写成 Schema、单测、质量门禁、CI 和安装后验证。

云枢当前最有价值的成果，不是某一个模型适配器或某一页界面，而是一套让“AI 能力、用户文件、原生权限、长期任务和发布流程”彼此可验证的工程边界。下一阶段的重点应从继续堆叠功能，转向提交历史收敛、模块拆分、真实端到端验证、连接器网络安全统一和正式发布可信度。
